Data flow

How a filter change on the Dashboard becomes updated numbers on screen.

  1. User changes a filter FilterBar updates the singleton refs in useFilters.js: period, warehouse, category, and order status.
  2. View reacts The view watches the filter refs and calls getCurrentFilters(), which maps the selected period to a month value.
  3. API client builds the request api.js adds only non-all filters as query params. The Dashboard fetches summary, orders, inventory and backlog in parallel.
  4. FastAPI filters in memory The route calls apply_filters (warehouse, category, status) and filter_by_month (month or quarter such as Q3-2025) over the in-memory lists.
  5. Response is validated Pydantic response models shape the JSON. The summary endpoint computes totals: inventory value, low-stock count, pending orders.
  6. View renders Raw responses are stored in refs. Derived values and chart data come from computed properties, and loading and error states are handled in the template.

Observations

Findings from reading the code. These are worth knowing before building on the system.

SeverityFinding
Gap The client calls /api/tasks (list, create, toggle, delete) and /api/purchase-orders (create, get), but main.py defines no such routes. These calls will return 404. PurchaseOrder and CreatePurchaseOrderRequest models exist without matching endpoints, and purchase_orders.json is an empty list.
Dead code Backlog.vue is not registered in the router. The backlog is only shown through the Dashboard and its detail modal.
Security CORS allows all origins with credentials, and there is no authentication. The API base URL is hard-coded to localhost. This is acceptable for a local demo only.
Design Writes do not persist: any data changed in memory is lost on restart. Quarter logic is duplicated between QUARTER_MAP and the quarterly report endpoint, and the data is fixed to 2025.
Strength Clear separation: one API client, one shared filter composable, and uniform filter semantics (all means no filter) across endpoints.
